## Context

当前仓库可以构建一个 Forge 1.20.1 Mod，但其根目录同时包含具体业务源码、飞机附属 Mod JAR、领域专用 skill、默认 Forge MDK 文档和个人代理/部署信息。现有公共入口直接引用客户端类，不能作为安全的双端模板；Gradle 元数据也分散在多处，当前构建还会受 Foojay 插件解析与代理环境影响。当前目录未检测到有效 Git 工作树，因此实施前不能依赖版本控制回滚已有文件。

本设计面向 specs 中的两个 capability：项目初始化负责生成一致、安全的工程结构；开发工作流负责代理、诊断、构建、编辑器和文档体验。

## Goals / Non-Goals

**Goals:**

- 让仓库成为复制后可一次性初始化的 Forge 1.20.1 模板，并保留初始化前的参数化状态。
- 将公共端、客户端和服务端权威逻辑的边界固化到目录和示例结构中。
- 让项目身份与 Mod 元数据只有一个规范化来源。
- 保留作者本机代理作为默认值，同时为其他环境提供无需修改受控默认文件的覆盖机制。
- 让初始化、诊断和构建失败具有可理解、可恢复的行为。

**Non-Goals:**

- 第一版不支持 Fabric、NeoForge、多加载器工程或 Minecraft 1.20.1 以外版本。
- 不提供向 CurseForge、Modrinth 或其他平台自动发布的流程。
- 不把当前 `health_control`、飞机加速功能或第三方 Mod JAR 迁移为模板示例。
- 不保证 PowerShell 初始化器可直接在非 Windows 平台运行；生成的 Gradle 项目需要具备跨平台构建能力。

## Decisions

### 1. 采用“Git 模板仓库 + 一次性 PowerShell 初始化器”

仓库保留参数化占位状态，用户复制或从模板创建仓库后运行 `scripts/init-template.ps1`，脚本执行预检、参数验证、目录重命名、文本替换、模块裁剪和结果验证。初始化成功后写入状态标记，阻止无确认的重复执行。

选择这一方案是因为它不引入 Cookiecutter、Node.js 或自定义 Gradle 插件等额外运行时，并与当前 Windows/PowerShell 开发环境一致。相比指导用户全局搜索替换，脚本可以验证 Forge ID、Java 标识符和目标文件状态，降低产生半初始化工程的风险。

初始化器在任何写操作前完成全部参数和文件冲突预检；实现阶段应优先采用临时工作目录或可恢复备份来避免中途失败污染项目。

### 2. 以 Gradle 属性作为项目元数据规范来源

`gradle.properties` 保存不涉及个人机器的项目身份与技术版本。`build.gradle` 的资源处理任务把这些属性展开到 `mods.toml` 和 `pack.mcmeta`，Java 包路径、主类名和资源命名空间由初始化器在初始化时确定。

不选择在多个 TOML、JSON 和 Java 文件中维护独立版本值，因为这种方式已经在当前仓库中产生了文档和项目身份漂移。

### 3. 代理使用“受控默认配置 + 本地覆盖 + 环境覆盖”

新增受版本控制的网络配置，默认启用 HTTP/HTTPS 代理 `127.0.0.1:7890`；增加被 Git 忽略的本地覆盖文件。优先级为显式系统属性或环境设置、本地覆盖、受控默认值。

代理配置必须在 Gradle 插件解析前生效，因此读取逻辑放在 `settings.gradle` 的 `pluginManagement` 阶段或等价的早期引导位置。禁用代理时不写入代理系统属性；诊断脚本会在构建前提示默认代理是否可达。

相比只在用户级 `GRADLE_USER_HOME/gradle.properties` 中配置，该方案能够随模板提供作者所需默认值；相比继续把 `systemProp.*` 散落在项目 `gradle.properties`，它能清晰表达覆盖与禁用语义。

### 4. 基础模板保持双端安全，可选功能按模块组合

公共 Mod 入口只包含公共 Forge API。客户端事件、按键和渲染代码进入独立 `client` 包并通过 Dist 限定加载；改变权威游戏状态的示例使用服务端事件或网络消息。

初始化器维护最小基础文件集，并为 Mixin、配置、网络通信和 GameTest 维护独立模块清单。模块选择负责同时加入源码、资源和 Gradle 配置，避免生成只有示例类却缺少依赖声明的项目。

默认选择空白模式和最小模块集，以减少新项目携带无关演示代码。示例模式用于验证客户端/服务端边界，不复用当前无敌开关实现。

### 5. 移除非必要的工具链自动下载插件

基础模板依赖已安装的 Java 17，并由 `scripts/doctor.ps1` 在构建前验证。Java toolchain 仍声明 17，但第一版不强制使用 Foojay resolver，以减少插件门户不可用时的额外失败点。

替代方案是保留 Foojay 自动下载 JDK；它对全新机器更便利，但会扩大网络与插件解析面，而当前仓库已经观察到该插件无法解析导致构建中止。后续可作为独立可选能力重新评估。

### 6. 文档、编辑器和 skill 都从具体业务中解耦

README 与开发指南采用简体中文，并仅保留通用 Forge 开发知识。现有飞机专用 skill 重写为通用 `forge-mod-development`，其中包括端侧判断、注册与事件选择、Mixin 决策、验证和构建流程。

VS Code 任务只引用仓库相对路径和 Gradle Wrapper。个人游戏实例路径、JDK 绝对路径、Mods 部署目录及第三方 JAR 不进入模板默认配置。

## Risks / Trade-offs

- [默认代理对未运行本地代理的用户会导致首次解析失败] → 初始化和诊断均展示代理状态，并提供单一明确的本地禁用入口。
- [一次性初始化需要重命名目录和替换多类文件，中途失败可能留下混合状态] → 所有验证前置，使用状态标记，并在实现时采用临时目录或可恢复备份后再提交结果。
- [可选模块组合数量增加验证成本] → 为最小、全模块及关键组合提供自动化生成与构建验证矩阵。
- [去除 Foojay 后新机器必须预装 Java 17] → `doctor.ps1` 在任何昂贵构建操作前检测并给出中文安装/配置指引。
- [模板固定版本会逐渐过时] → 版本全部集中在规范属性中，升级 Minecraft、Forge 或 Gradle 时通过独立 OpenSpec change 处理。
- [PowerShell 限制非 Windows 用户直接初始化] → 第一版明确限制初始化平台，同时保证初始化后的 `gradlew` 与项目源码不依赖 Windows 绝对路径。

## Migration Plan

1. 记录当前仓库中需要保留的通用 Forge、Mixin、代理和构建经验，确认旧业务文件清单，并在删除或替换前建立可恢复的本地迁移备份。
2. 建立参数化项目身份、基础源码/资源结构和 Gradle 元数据生成机制。
3. 实现代理默认配置、本地覆盖、环境诊断和统一构建入口。
4. 实现初始化器、初始化状态检查、空白/示例模式及可选模块裁剪。
5. 通用化 VS Code 配置、中文文档、OpenSpec 配置和 Forge 开发 skill。
6. 删除旧业务源码、第三方 JAR、个人部署信息与生成物，并执行最小和全模块生成验证。
7. 对生成项目执行干净构建、客户端启动检查和专用服务器类加载检查。

如果迁移失败，使用实施前创建的本地迁移备份恢复；若后续建立了 Git 工作树，再将初始化器开发与模板清理拆分为可审查的小提交，避免依赖不可恢复的手工删除。
